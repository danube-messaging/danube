## Friction & findings from `v0.17.0`

1. **`cluster_status` and `get_cluster_balance` are `cluster`-mode only:** in `standalone` mode both return `Operation is not implemented or not supported ("cluster operations not available in standalone/edge mode")`. `health_check`, `list_brokers`, `get_broker_logs`, and `get_cluster_metrics` fallback all work in `standalone` mode. Updated Task 01 and `01_bootstrap_and_cluster_ops.sh` accordingly.
2. **Schema metadata split between `create_topic` and `configure_topic_schema`:** calling MCP `create_topic` with `schema_subject` does not populate topic schema validation config (`get_topic_schema_config` returns `No schema configured`), and calling `configure_topic_schema` does not populate `schema_subject` in `danube topic describe`. Agents enforcing schemas must call `configure_topic_schema` explicitly.
3. **JSON Schema default compatibility is `BACKWARD`:** adding a new required field passes `BACKWARD` compatibility (only `FORWARD` rejects added required fields), while removing an existing required field fails `BACKWARD`.
4. **No online `issue_token` tool in MCP:** `danube mcp` exposes offline `create_token` (requiring `secret_key`), while `cluster_export_config` rightly redacts `jwt.secret_key`. In Task 06, an agent without access to `tls/jwt.secret` must use CLI `danube auth token issue` to mint service-account tokens.
5. **`explain_consumer_stall` reports stale backlog after short-lived `danube consume --limit N`:** even after `danube consume` received and acked all 10 backlog messages (`Drained lines: 10`) and waiting `6s` past the cursor debounce window, `explain_consumer_stall` still reported `Backlog: 11` because `get_subscription_cursor` returned `None` (no cursor entry persisted into Raft by the short-lived consumer before exit, so `explain_consumer_stall` fell back to `wal_head`).
6. **`set_subscription_failure_policy` applies at subscription creation time:** calling MCP `set_subscription_failure_policy` on an already-subscribed live subscription persists the policy to Raft metadata, while the active in-memory dispatcher keeps the initial policy until recreated. Setting the failure policy *before* subscribing takes effect immediately.
